Validation & known limitations

How well does TripLibre reconstruct a day? This page separates three kinds of evidence: what has been observed in everyday use, what the automated tests guarantee, and the formal benchmarking that has not been done yet.

!

All accuracy numbers so far come from one person's phone over 17 days, scored against that person's own corrected diary. They describe that sample, not TripLibre in general. Please don't cite them as a general accuracy figure.

Observed in real-world use

Situations the developer has lived through and checked in the diary, mostly in Philadelphia:

ScenarioUsually worksKnown to go wrong
Walking between buildingsWalks over a few hundred metres become their own trip.Buildings under about 100 m apart, with no fix in between, merge into one stay.
Indoor GPS driftOrdinary drift at home or the office is filtered out.Large venues can drift hundreds of metres and produce duplicate stays 200–500 m apart.

Automated tests

Run on every push and pull request (.github/workflows/ci.yml). None of them use real location data.

  • Core suite (make test): 112 Swift tests in 11 suites, covering inference, edits, reprocessing, export, analytics, stamps and widgets. Fourteen of them are the synthetic scenarios from the original product brief: home–work–home, a trip chain, a walking trip, subway, car, a multimodal trip, a brief stop that must not become a visit, a long stationary period, GPS drift while stationary, a missing GPS interval, an overnight visit, crossing midnight, airport–flight–airport, and several days without opening the app. Others cover daylight-saving time and check that incremental processing equals a one-shot rebuild.
  • Calibration regressions (CalibrationTests): one synthetic fixture per failure class found on real data. Each fails on the engine version before the fix.
  • Export contract (make export-check): Swift writes a real export, Python loads it, and the CSV and SQLite versions must agree.
  • Replay determinism (make calibrate-smoke): a synthetic fixture replayed twice must give byte-identical output, then the full evaluation pipeline runs on it.
  • UI tests (make ui-test): core flows and accessibility audits in the simulator, on demo data.

Personal calibration study

Issue #46 replayed one phone's raw data through the engine and compared it with the same person's corrected diary. The days were split into calibration days (for tuning) and validation days (scored once) before any tuning. The full protocol, metrics and adverse tradeoffs are in docs/research/inference-calibration.md.

Round 2 tuned mode detection. On the 17 calibration days (in-sample), group-level mode accuracy on human-labelled trips rose from 0.51 to 0.82; exact mode accuracy rose from 0.39 to 0.54. The held-out check for round 2 is still pending, because no new days had been recorded after the cutoff.

The study publishes aggregates only. The raw data and per-day reports stay on the developer's machine.

Planned benchmarking

Planned Nothing in this section has been done yet. It defines what a formal evaluation should report, so that results can be compared across versions and studies.

Metrics

AreaMetric
Stays and tripsPrecision, recall and F1 under the one-to-one matching rules of the calibration study; split and merge counts.
TimingSigned and absolute arrival and departure error (median, mean, p90).
Whole dayShare of minutes where the diary and the truth agree on "at a place" versus "travelling".
ModeExact and group-level accuracy, and a confusion matrix, on independently labelled trips.
CompletenessShare of each day with collection running; days with gaps over 15 minutes; trips flagged has_gap.
BatteryBattery drain per day attributable to TripLibre, by collection profile and device model.
Correction burdenEdits per person-day and time spent correcting.

Ground truth

The calibration study used the user's own corrections as truth, which risks agreeing with itself. A formal benchmark should use an independent reference: a researcher-kept log, a scripted route with timestamps, or a second device. It should also report uncertainty (for example, day-level bootstrap intervals) and keep a held-out set.

Reproducible fixtures

Real GPS logs can't be shared without exposing the people in them. Planned fixtures are synthetic or carefully de-identified (shifted, rotated, time-offset) traces that reproduce a failure class, stored as SQLite files that hht-calibrate replay can read. See proposing an inference test case.

Known limitations

  • Unobservable stops. A stop with no GPS fix at all can't be detected. The user has to add or stamp it.
  • Walks during GPS silence. When the collector is quiet, a walk can be absorbed into a stay or the next trip. Arrival after a silent walk is dated from the next fix.
  • Collector holes while driving. Recurring 4–6 minute silences while in a vehicle make routes and distances straight lines across the gaps.
  • Nearby buildings merge, and large venues duplicate stays, as described above.
  • Mode is the weakest part. Taxi, bus, light rail and commuter rail are never predicted directly; driver versus passenger is never inferred.
  • The engine's first answer is lost when you edit. Records are updated in place, so the app's real-world accuracy can only be estimated by replay, not read from use. Keeping the original is Planned.
  • No engine version field. A replay is pinned by git commit and configuration, not by a version stored with each record.
  • iOS only, and background behaviour depends on iOS power management, which varies by device and iOS version.
